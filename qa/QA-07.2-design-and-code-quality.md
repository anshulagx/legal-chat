# QA 7.2 · Design and code quality

**Decision to make.** The reviewed design supports the complete existing product, the frontend/backend audits have actionable closure, and redesign/refactoring preserved the established contracts.

**Sources.** [Detailed phase plan](../Phase_7.2_Plan.md) · [Implementation plan](../Implementation_Plan.md) · [PRD acceptance flows](../Legal_Support_Chat_PRD.md) · [Phase 07 guide](QA-07-failure-recovery-observability-and-accessibility.md).

## Setup

Review the locally committed integrated candidate from a clean checkout. Record its SHA, startup instructions, fixture versions, tool versions and origin. Use an isolated disposable Mongo replica set, fictional agreement/amendment/shared-policy fixtures, two customer profiles and a separate admin. Use existing test-only fault controls. Record baseline failures separately. Require the critique, code audit, design proposal and Anshul's design-review outcome before judging implementation against the agreed direction.

## Required checks

1. **7.2.1 · Audit evidence and closure.** Trace every finding to code, reproduction or screenshot. Verify each fixed defect using its original reproduction. Require zero unresolved P0/P1 findings, an implemented agreed P2 scope, explicit acceptance for P2 deferrals, and evidence-backed dispositions for all other findings. Inspect frontend and backend changes independently, including contract/migration changes. Do not equate a refactor or scanner result with a verified fix.
2. **7.2.2 · Design fidelity and task clarity.** Compare the app with the reviewed mockups and state specification at 320, 390, 768 and 1280 CSS px. Capture auth, fresh chat, long chat, uploads/comparison, sources and admin. Verify consistent hierarchy, readable content, identifiable actions and document sides, visible attachment scope/readiness and actionable errors. Record task outcomes and observed friction; subjective approval needs Anshul's review, while behavioral requirements need observed evidence.
3. **7.2.3 · Local acceptance replay.** Complete all six PRD flows except the explicitly phase-08 hosted/Compose portions. Verify streamed cited answers and exact sources; both comparison sides; absent-term draft/copy; new/reopened chat and account isolation; policy replacement/historical citations/admin denial; failure, partial reply, retry delay, cancellation, restart and logout. Record expected and actual results with one evidence reference per flow.
4. **7.2.4 · Interaction edge cases.** Read earlier messages during streaming without unwanted scroll jumps; return to latest; submit after a long reply; open/close mobile history; use the composer with the mobile keyboard; inspect long filenames and comparisons. Switch chats under delayed responses, expire a session and dismiss a source while loading. Verify stale results do not replace the selected view and cleanup does not lose durable questions, attachments or attempts. Test fixes to these paths with targeted automated coverage where warranted.
5. **7.2.5 · Accessibility.** Scan signup, login, chat, source viewer and admin. Manually check keyboard order, visible/unobscured focus, drawer/dialog Escape and focus return, citation previews, touch use, contrast, 320 CSS px reflow and native 200% zoom. Complete the observed screen-reader walkthrough on the final candidate: stage/completion, errors, file readiness, comparison order and focus stability. Resolve scanner incomplete items with evidence. Do not substitute CSS zoom or axe for native zoom or screen-reader observations. An unavailable mandatory observation keeps this gate BLOCKED and cannot close phase 07.4.
6. **7.2.6 · Code and regression checks.** Run the commands below using Node 22+, plus any new audit/static-analysis and targeted test commands documented in the handoff. Review types, runtime validation and the high-risk invariants identified in the detailed plan. Require no untriaged new advisory findings; record any inaccessible dependency-advisory service. Run live integration probes when provider/storage/retrieval contracts changed, and state what deterministic fixtures do not establish.

```sh
npm run build
npm run test:phase01
npm run test:wave-02
npm run test:wave-03
npm run test:wave-04
npm run test:wave-05
npm run test:wave-06
npm run test:wave-07
```

Set `QA_MONGODB_URI` in the process environment to the documented disposable replica set for every applicable suite; phase 01 otherwise uses a different historical default. Use the browser-tool setup documented in the README for existing browser checks and include any new checks in the handoff. Earlier test totals are historical evidence, not the expected result of this candidate.

## Verdict and release dependency

Write `qa/phase07.2-qa-report.md` with candidate SHA, environment, design-review reference, finding dispositions and one row per check: expected behavior, actual observation, evidence and PASS/FAIL/BLOCKED. Include before/after captures, exact test commands/results and limitations. PASS requires every mandatory check to pass; missing observations are BLOCKED and mismatches are FAIL. Send failures to the responsible implementer, then review the updated candidate and rerun affected checks and regressions.

After independent PASS, follow the implementation plan's GitHub checkpoint procedure. Phase 08 must use this integrated candidate or an independently reverified successor. Both phase 07 and 7.2 must be PASS before release advancement.
